# Agent Spec — Enterprise Trip-Planner Mesh

## Overview

A three-agent A2A mesh on Google Cloud Agent Platform demonstrating enterprise governance:

- **trip-planner** — orchestrator; delegates to specialists via `RemoteA2aAgent`
- **flight-researcher** — flight search specialist (A2A service)
- **hotel-researcher** — hotel search specialist (A2A service)

Each agent lives under `src/<agent>/` as an agents-cli project. Authorization is **per agent**: a user allowed to call trip-planner is not automatically allowed to use flight or hotel specialists.

## GCP constraints

| Setting         | Value                                                               |
| --------------- | ------------------------------------------------------------------- |
| Project         | `yexperiment`                                                       |
| Region          | `asia-northeast1`                                                   |
| Access          | Private only; no public endpoints                                   |
| Deploy identity | Impersonate `agent-operator-sa`; each agent uses its own runtime SA |

## Example use cases

1. **Full access:** "Plan a trip from NYC to San Francisco next week" → flights + hotels in one plan.
2. **Flight-only persona:** Same prompt → flights returned; hotel step fails with explicit auth error.
3. **Hotel-only persona:** Inverse of above.
4. **Denied user:** Blocked at gateway ingress.

## Tools required

| Agent             | Tool             | Purpose                                                               |
| ----------------- | ---------------- | --------------------------------------------------------------------- |
| flight-researcher | `search_flights` | Mock deterministic flight options (hybrid: optional live API via env) |
| hotel-researcher  | `search_hotels`  | Mock deterministic hotel options (hybrid: optional live API via env)  |
| trip-planner      | A2A delegation   | Calls flight-researcher and hotel-researcher with user context        |

## Governance personas (auth matrix)

| Persona            | trip-planner | flight-researcher | hotel-researcher |
| ------------------ | :----------: | :---------------: | :--------------: |
| `mesh-full-user`   |    allow     |       allow       |      allow       |
| `mesh-flight-user` |    allow     |       allow       |       deny       |
| `mesh-hotel-user`  |    allow     |       deny        |      allow       |
| `mesh-deny-user`   |     deny     |       deny        |       deny       |

Local dev: use deployed mesh or local A2A servers (see `docs/guides/01-local-mesh.md`). Persona governance is enforced by Agent Platform IAP, not env vars.

## Constraints and safety rules

- Never deploy without explicit human approval.
- Never commit secrets, `.env`, or OAuth client secrets.
- Never skip offline eval before deploy discussion.
- Orchestrator must propagate user identity on A2A calls.
- Negative auth outcomes must be visible to the user (not silent skip).

## Success criteria

- [ ] Three agents scaffolded under `src/` and run locally via A2A
- [ ] Offline eval baselines for each agent + orchestrator E2E
- [ ] Terraform SAs/IAM in `terraform/`; operator impersonation documented
- [ ] Deployed to Agent Runtime (private) in `yexperiment` / `asia-northeast1`
- [ ] Agent Registry + gateway + agent-to-agent IAP policies applied
- [ ] All four personas tested (positive and negative)
- [ ] Junior guides under `docs/guides/`

## Architecture

- Deployment target: **Agent Runtime** (`agent_runtime`)
- Specialists: `--agent adk_a2a`
- Orchestrator: standard `adk` with `RemoteA2aAgent`
- Mesh governance: Agent Gateway ingress + IAP agent-to-agent policies
